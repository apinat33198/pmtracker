PM Tracker เป็น Go binary ตัวเดียว ใช้ standard library เท่านั้น (ไม่มี dependency ภายนอก, ไม่ใช้ CGO) เก็บข้อมูลในไฟล์ JSON ไฟล์เดียว และ render หน้าเว็บจากฝั่ง server ด้วย html/template JavaScript มีแค่ส่วนเล็ก ๆ ที่ช่วยเรื่องการใช้งาน ฟอร์มทุกฟอร์มทำงานได้แม้ปิด JavaScript

Package

Packageหน้าที่
cmd/pmtrackerอ่าน flag, โหลด config, เปิด store, เชื่อมทุกส่วน, สร้างข้อมูลตั้งต้นครั้งแรก, รันงานเบื้องหลัง (sync, backup, digest) และคำสั่ง check, sync, digest, hash-password
internal/configอ่านและตรวจ config.json, ค่าเริ่มต้น, timezone, วันหยุด, trusted proxies, บทบาท
internal/coreโดเมนทั้งหมด ไม่มี I/O: catalog (site, system, vendor, task, calendar), matcher, forecaster, snapshot, job, finding, incident, ตัววัด, import CSV, digest, ฟีด ICS
internal/storeไฟล์ JSON: catalog, event ที่ mirror มา, การตัดสิน, กฎ, การยืนยัน visit, visit ที่บันทึกเอง, job, finding, incident, ผู้ใช้, กุญแจ session; activity log ในไฟล์รายวันแยก
internal/gcalclient ของ Google Calendar (service account, JWT ที่เขียนเอง), อ่าน events.list ทีละหน้า, syncer ที่จัดการ sync token และ 410 Gone
internal/webHTTP server: route, sign in, บทบาท, ทุกหน้า, admin, CSV, template, CSS, คู่มือนี้
internal/authhash รหัสผ่าน (PBKDF2-SHA256), cookie session ที่เซ็นด้วย HMAC, ตัวจำกัดการลองรหัสผิด
internal/backupสำรองรายวัน, ลบอันเก่า, อ่านไฟล์สำหรับ restore
internal/notifyส่ง Telegram และตัวตั้งเวลารายวัน
internal/demoข้อมูล demo 21 site, ปฏิทินปลอม, job, finding และ incident ตัวอย่าง

ทิศทางการพึ่งพา: web → store, gcal, backup → core → config ส่วน core ไม่รู้จัก HTTP หรือไฟล์ จึงเทสต์ได้ง่าย

เส้นทางของ request

  1. web.Server.authenticate อ่าน cookie session (หรือ basic auth) หา user และใส่ไว้ใน context ตรวจ Origin และ Sec-Fetch-Site สำหรับ POST ใส่ security header
  2. web.Server.need ตรวจบทบาทของ route (viewer, editor, admin) ไม่พอได้ 403 ยังไม่ sign in ถูกพาไปหน้า login
  3. handler เรียก web.Server.snapshot ซึ่งคือ store.Store.Inputs (สำเนาข้อมูลทั้งหมด) ส่งต่อให้ core.Build
  4. core.Build คำนวณทุกอย่างใหม่ทุก request: จับคู่ทุก event ด้วย matcher, สร้าง visit, คำนวณ forecast ของทุก task, สรุปต่อ site และ vendor, inbox, job, finding, incident ไม่มี cache ข้อมูลจึงตรงกับไฟล์เสมอ
  5. web.Server.renderCode ใส่ข้อมูลลง page แล้ว render template ของหน้านั้นใน layout.html

การเปลี่ยนข้อมูล (POST) เรียก method ของ store เช่น store.Store.UpdateCatalog หรือ store.Store.AddIncident ซึ่งตรวจข้อมูล บันทึกไฟล์ และเขียน activity log จากนั้น redirect กลับพร้อมข้อความที่เซ็นไว้ (web.Server.redirect)

การ sync ปฏิทิน

  1. gcal.Syncer.Run เรียก gcal.Syncer.TrySyncAll ทันทีและทุก sync_interval_minutes (ข้ามรอบถ้ายังทำรอบก่อนไม่เสร็จ)
  2. แต่ละปฏิทิน gcal.Syncer.syncOne เรียก gcal.Google.List ด้วย sync token เดิม (อ่านเฉพาะที่เปลี่ยน) ถ้ายังไม่มี token อ่านทั้งหมดตั้งแต่ sync_lookback_months ถ้า Google ตอบ 410 Gone อ่านทั้งหมดใหม่
  3. store.Store.ApplySync รวม event เข้า mirror: event ที่ถูกยกเลิกเก็บไว้แต่ mark cancelled, การเลื่อนวันบันทึกเป็น change, sync เต็มลบ event ที่หายไป sync ที่ไม่มีอะไรเปลี่ยนไม่เขียนไฟล์
  4. ไม่มีการเก็บผลการจับคู่ไว้ request ถัดไปจะจับคู่ใหม่จาก mirror ทันที

งานเบื้องหลัง

  • sync: goroutine ของ gcal.Syncer.Run
  • backup: backup.Manager.Run สำรองตามเวลาที่ตั้ง ลบไฟล์เก่า และสำรองที่พลาดไปตอนเริ่มทำงาน
  • digest: notify.Daily เรียก core.Digest แล้วส่งด้วย notify.Telegram.Send
  • ทั้งหมดหยุดเมื่อได้ SIGTERM ผ่าน context เดียวกับ HTTP server

หลักการออกแบบ

  • สถานะทั้งหมดคำนวณใหม่ จากข้อมูลดิบทุกครั้ง (event, การตัดสิน, การยืนยัน, catalog) ไม่มีสถานะที่เก็บไว้แล้วอาจไม่ตรง
  • อ่านปฏิทินอย่างเดียว ไม่เขียนกลับ Google
  • ตรวจข้อมูลใน core: ทุก record มี Clean() ที่จัดข้อความและตรวจค่า ใช้ทั้งตอนบันทึกและตอน restore
  • ทุกการเปลี่ยนแปลงมี activity: method ของ store รับข้อความ action และเขียนลง activity log หลังบันทึกไฟล์สำเร็จ
  • job, finding และ incident ไม่แตะสถานะ PM แยกจาก forecast โดยสิ้นเชิง
  • ข้อความในแอปเป็นภาษาอังกฤษเรียบง่าย บอกว่าเกิดอะไรและต้องทำอะไรต่อ ข้อความ error บอกวิธีแก้
