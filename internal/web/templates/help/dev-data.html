ข้อมูลทั้งหมดอยู่ในไฟล์ JSON ไฟล์เดียว (data_file ในเซิร์ฟเวอร์นี้คือ {{.Cfg.DataFile}}) อ่านเข้าหน่วยความจำตอนเริ่ม และเขียนใหม่ทั้งไฟล์ทุกครั้งที่ข้อมูลเปลี่ยน ปริมาณข้อมูลน้อย (21 site, visit ไม่กี่ร้อยครั้งต่อปี) แบบนี้จึงพอ และ method ของ store ออกแบบให้ย้ายไปเป็นตาราง SQL ได้ตรง ๆ

ไฟล์บนเซิร์ฟเวอร์

ไฟล์มีอะไร
data.jsonข้อมูลทั้งหมด สิทธิ์ 0600 อ่านได้เฉพาะ service
data-activity/activity-YYYY-MM-DD.jsonlactivity log วันละไฟล์ (วันตาม UTC) หนึ่งบรรทัดต่อหนึ่งรายการ เขียนต่อท้ายอย่างเดียว ลบไฟล์ที่เก่ากว่า activity.keep_days
backups/pmtracker-YYYY-MM-DD.json.gzสำรองรายวัน, …-HHMMSS-manual.json.gz จาก Back up now และ …-before-restore.json.gz ก่อน restore
data.json.before-updateสำเนาที่ install.sh และ push.sh ทำไว้ก่อนอัปเดตโปรแกรม

demoไฟล์ที่สร้างโดย -demo (demo จะไม่ทับไฟล์ที่ไม่ใช่ demo)

การเขียนไฟล์

  1. method ของ store ล็อก แก้ข้อมูลในหน่วยความจำ และตรวจ (Clean, Validate, CheckLinks)
  2. store.Store.write เขียนทั้งไฟล์ลง temp file ในโฟลเดอร์เดียวกัน, fsync, rename ทับไฟล์เดิม และ fsync โฟลเดอร์ ไฟล์จึงไม่เสียแม้ไฟดับกลางคัน
  3. ถ้าเขียนไม่สำเร็จ ข้อมูลในหน่วยความจำย้อนกลับ และ activity ของการเปลี่ยนนั้นถูกทิ้ง
  4. ถ้าสำเร็จ จึงเขียน activity log (และสำเนาลง log ของเซิร์ฟเวอร์ activity: …)

sync ที่ไม่มีอะไรเปลี่ยนอัปเดตเฉพาะในหน่วยความจำ ไม่เขียนไฟล์ ถ้าโปรแกรมรีสตาร์ตก่อนการเขียนครั้งถัดไป sync token เดิมยังใช้ได้ และระบบจะอ่านการเปลี่ยนแปลงนับจากนั้นมาใหม่

การตรวจตอน restore

  • อ่านแบบ strict: key ที่ไม่รู้จักทำให้ไม่ผ่าน
  • เวอร์ชันใหม่กว่าโปรแกรม: ปฏิเสธพร้อมบอกให้อัปเดตโปรแกรมก่อน
  • ตรวจ catalog, job, finding และ incident ทุกรายการ (เลขไม่ซ้ำ, เลขอ้างอิง incident ไม่ซ้ำ, ผ่าน Clean)
  • ลิงก์ที่ชี้ไปของที่ไม่มีถูกตัดทิ้งแทนการปฏิเสธ
  • ใช้กุญแจ session เดิมของเซิร์ฟเวอร์ และเพิ่ม epoch ทุกบัญชี (ทุกคนถูก sign out)

ผลวัดสำหรับ production

สรุป: ขนาดนี้ไฟล์ JSON ไม่ใช่คอขวด สิ่งที่ต้องระวังใน production:

  • RPO: สำรองวันละครั้งบนดิสก์เดียวกัน อาจเสียข้อมูลได้ถึง 1 วัน แก้ด้วย backup.dir บน NAS และ Proxmox Backup Server
  • restore แทนที่ทั้งหมด รวมสิ่งที่บันทึกหลังไฟล์สำรอง
  • ประวัติ PM เก่ากว่า sync_lookback_months หายเมื่อ Google ให้ sync ใหม่ทั้งหมด
  • ต้นทุนโตตามข้อมูล: ทุกหน้าคำนวณใหม่จากข้อมูลทั้งหมด ทุกการเปลี่ยนเขียนทั้งไฟล์ ใช้ได้ดีถึงราว 5 MB
  • ไม่มีที่เก็บไฟล์แนบ (รูป รายงาน vendor)

ขั้นต่อไป: SQLite

ย้ายเมื่อเริ่มแนบรูปหรือรายงาน, ไฟล์เกินราว 5 MB, หรือต้องเก็บประวัตินานขึ้น:

  • modernc.org/sqlite (pure Go ไม่ใช้ CGO, ยังเป็น binary ตัวเดียว) เป็น dependency ภายนอกตัวแรก
  • WAL mode, หนึ่งตารางต่อชนิดข้อมูล, visit เป็นแถวของตัวเอง (ประวัติไม่ขึ้นกับ mirror ของปฏิทิน), timeline ของ incident เป็นตาราง insert-only, หน้าเว็บ query เฉพาะที่ต้องแสดง
  • ไฟล์แนบเก็บบนดิสก์ตั้งชื่อด้วย SHA-256 ข้อมูลไฟล์อยู่ใน SQLite
  • VACUUM INTO รายคืน และ Litestream ส่งต่อแบบต่อเนื่องไป S3 (MinIO บน NAS หรือ Cloudflare R2) ทำให้ RPO เหลือไม่กี่วินาที
  • ย้ายข้อมูลโดย import data.json ครั้งเดียวตอนเริ่ม และเก็บรูปแบบ JSON export ไว้สำหรับ backup และย้ายเซิร์ฟเวอร์
