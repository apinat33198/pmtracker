เริ่มพัฒนา

git clone https://github.com/apinat33198/pmtracker && cd pmtracker
go run ./cmd/pmtracker -demo                     # http://localhost:8080 (admin / editor / viewer, รหัส demo)
go run ./cmd/pmtracker -demo -today 2027-01-15   # สมมติว่าเป็นวันอื่น
go run ./cmd/pmtracker -demo -keep               # เก็บสิ่งที่แก้ไว้ข้ามการรีสตาร์ต
go test ./...
go vet ./...

build ด้วย Go รุ่นที่ยังได้ security fix (1.26 หรือ 1.27 ณ พ.ย. 2026) รัน govulncheck ./... เป็นระยะ

เทสต์

  • internal/core: matcher, forecast, การบวกเดือน, roll-up, import, job, finding, incident (การตรวจ, ลิงก์, ระดับความเสี่ยง, ตัววัด, matrix)
  • internal/store: บันทึกและอ่านกลับ, การล้างลิงก์, restore ที่ปลอดภัย, activity log, timeline ที่แก้ไม่ได้, sync ที่ไม่เขียนไฟล์
  • internal/web: ทุกหน้า render ได้โดยไม่มีค่าที่หายหรือไม่ปลอดภัย, บทบาท, admin, sign in (session, cookie ปลอม, cross-site POST, open redirect, lockout), flow ของ job, finding, incident และคู่มือนี้
  • เทสต์ web ใช้ demoServer ซึ่งตั้งนาฬิกาไว้ที่ 3 พ.ย. 2026 09:00 ผลจึงคงที่

แนวทางเขียนโค้ด

  • standard library เท่านั้น ถ้าจะเพิ่ม dependency (เช่น SQLite) ให้ตัดสินใจเป็นเรื่องเป็นราว
  • ตรรกะอยู่ใน core handler ใน web แค่อ่านฟอร์ม เรียก store และ render
  • ข้อความในแอปเป็นภาษาอังกฤษเรียบง่าย บอกว่าเกิดอะไรและทำอะไรต่อ error บอกวิธีแก้ (“enter the root cause before closing it”) ไม่ใช่รหัส error
  • ทุกการเปลี่ยนข้อมูลมี action สำหรับ activity log ที่บอกว่าอะไรเปลี่ยนในบรรทัดเดียว
  • ป้องกันสูตร CSV ด้วย web.csvCell ทุกช่องที่เป็นข้อความจากผู้ใช้
  • template ใช้ html/template ซึ่ง escape ให้เอง ไม่ใช้ template.HTML กับข้อมูลผู้ใช้

เพิ่มข้อมูลชนิดใหม่: เช็กลิสต์

ใช้ job, finding และ incident เป็นตัวอย่าง:

  1. core: struct, ตัวเลือก ([]Choice), Clean() ที่จัดข้อความและตรวจทุกค่า, CheckLinks() ถ้าอ้างถึงของอื่น, view สำหรับแสดงผล, ฟังก์ชัน build ที่เรียงลำดับ, ตัววัด เพิ่มลง Inputs และ Snapshot และ core.Build
  2. store: field ใน state (มี omitempty), รวมในการหา next_id ใน normalize, ฟังก์ชัน tidy ที่ล้างลิงก์เมื่อของที่อ้างถึงหายไป (เรียกใน normalize และ cleanup), ฟังก์ชันตรวจตอน restore, method Add/Update/Delete ที่ย้อนกลับเมื่อบันทึกไม่สำเร็จ, เพิ่ม currentVersion ถ้าต้องให้ main รุ่นเก่าปฏิเสธไฟล์สำรอง
  3. web: handler, route พร้อมบทบาท (ลบที่เป็นหลักฐานให้ admin เท่านั้น), template, ฟังก์ชัน template สำหรับตัวเลือก, CSV, ลิงก์จากหน้าที่เกี่ยวข้อง, ตัวเลขในเมนูถ้าควรมี
  4. digest ถ้ามีสิ่งที่ต้องตามทุกวัน
  5. demo: ข้อมูลตัวอย่างที่ผ่าน Clean และเทสต์ที่ render ทุกหน้า
  6. เทสต์ทั้งสามชั้น และ README
  7. คู่มือนี้ (ข้อถัดไป)

ดูแลคู่มือนี้

  • หน้าคู่มืออยู่ที่ internal/web/templates/help/<slug>.html แต่ละไฟล์ define helpbody ลำดับ กลุ่ม ชื่อ และคำอธิบายของหน้าอยู่ใน helpPages ใน internal/web/help.go
  • หน้าคู่มือใช้ฟังก์ชัน template ของแอปได้ เช่น consequenceScale, findingSeverities และอ่านค่า config ได้ที่ .Cfg ดังนั้นตาราง rating และค่าเริ่มต้นในคู่มือตรงกับโค้ดและเซิร์ฟเวอร์เสมอ ใช้แบบนี้แทนการพิมพ์ค่าเองเมื่อทำได้
  • <h2 id="…"> กลายเป็นรายการ “ในหน้านี้” อัตโนมัติ
  • รูปหน้าจออยู่ที่ internal/web/static/help/*.webp (กว้าง 1000 px คุณภาพ 72) ถ่ายจากโหมด demo
  • เทสต์ TestHelp… ตรวจว่า: ทุกหน้าใน helpPages มีไฟล์และ render ได้, ลิงก์ภายในทุกลิงก์เปิดได้ (รวม #anchor ในคู่มือ), และทุกชื่อใน <code class="fn"> ในหน้า ฟังก์ชันหลัก มีอยู่จริงในโค้ด

เปลี่ยนเกณฑ์ความเสี่ยงของ incident

ถ้านโยบายความเสี่ยงของบริษัทใช้เกณฑ์อื่น แก้ใน internal/core/incidents.go ที่เดียว:

  • ConsequenceScale และ LikelihoodScale: ชื่อและคำอธิบายของแต่ละระดับ (ต้องมี 5 ระดับ เพราะ matrix เป็น 5 × 5)
  • RiskBands: ชื่อ คำอธิบาย และคะแนนต่ำสุดของแต่ละช่วง

หน้าฟอร์ม หน้า Incidents และคู่มือนี้อ่านจากค่าเหล่านี้ทั้งหมด จึงเปลี่ยนตามกันทันที ข้อมูลที่บันทึกไว้เก็บเป็นตัวเลข 1 ถึง 5 จึงไม่ต้องย้ายข้อมูล แต่ระดับของ incident เดิมจะคิดใหม่ตามช่วงคะแนนใหม่ ปรับเทสต์ TestRiskBands ตาม
